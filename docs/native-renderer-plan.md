# Нативный рендер для Switch: план

Цель — 30 fps на стоковых частотах без урезания графики. Сейчас кадр рисует эмуляция GPU Xbox 360 из SDK. Её
поток «GPU Commands» — главный тормоз (см. `portlog.md` §16.11–16.12).

## Что известно

| Факт | Значение |
|---|---|
| Draw на кадр (геймплей) | ~3900 |
| Цена одного draw в эмуляции SDK | ~7.5 мкс на быстром ядре ПК → на Cortex-A57 1 ГГц ~30–45 мкс |
| Бюджет на draw для 30 fps на Switch | ≤ 8 мкс, включая драйвер NVK |
| masseffect-nx (свой рендер) | ~730–2500 draw, 13–40 мкс на draw на A57, итог ~25 fps |
| Шейдеры игры | готовые контейнеры Xenos (`0x102A1100/1101`) в `Global.big` / `SeekFreeBoot.big`, около 150 VS + 150 PS — можно транслировать заранее |
| Потоки игры | самый занятый ~41% ядра ПК, из них ~65% ожидание; реальная цена на Switch не измерена |

Вывод: рендер уровня masseffect-nx нужен, но одного его мало — draw в 2–5 раз больше, чем у них. Нужны ещё
дешёвый путь draw (≤ 8 мкс) и, возможно, меньше draw без потери картинки (объединение, отсечение невидимого).

## Архитектура (по образцу masseffect-nx)

```
игра (свой Direct3D, статически в XEX)
   |  пишет PM4-пакеты в кольцевой буфер
   v
поток кольца: разбор PM4 -> зеркало регистров -> запись draw в Vulkan
   |                                   |
   |              (worker) запись команд в NVK
   v                                   v
fence / read pointer для игры     очередь Vulkan -> вывод
```

- Эмуляция GPU из SDK (трансляция шейдеров на лету, защита страниц памяти) не загружается.
- Шейдеры — заранее собранная библиотека: контейнер Xenos → HLSL (XenosRecomp) → SPIR-V (DXC), поиск по хэшу.
- EDRAM — по одному Vulkan-образу на формат и переносы между ними («mode 4» masseffect-nx), с правилами
  Sleeping Dogs: 7e3-буфер света, резолв как integer, MSAA-очистка стенсила (уже разобраны на стенде).
- Вершины и индексы копируются в момент draw (без слежения за страницами), одинаковые диапазоны кадра — один раз.

## Этапы

| # | Этап | Результат | Проверка |
|---|---|---|---|
| 0 | Замеры | цена потоков игры (символы для сгенерированного кода), PM4-пакеты и draw по проходам кадра | цифры в portlog |
| 1 | Библиотека шейдеров | извлечение контейнеров из `.big`, XenosRecomp + DXC, упаковка, покрытие 100% по RenderDoc | все шейдеры кадров транслируются и валидны |
| 2 | Каркас рендера | поток кольца, разбор PM4, зеркало состояния, вывод кадра — сначала меню и UI | меню на стенде совпадает с эмуляцией |
| 3 | Сцена | EDRAM mode 4, резолвы, текстуры, правила Sleeping Dogs | кадры геймплея совпадают с эмуляцией (сравнение резолвов) |
| 4 | Скорость | бюджет ≤ 8 мкс на draw: кэши, без аллокаций, отложенная запись, дедупликация | мкс на draw на стенде, затем на консоли |
| 5 | Меньше draw | отсечение и объединение там, где картинка не меняется | draw/кадр и fps |

Работа идёт на ПК-стенде (`nx/desktop`), рендер включается cvar'ом, эмуляция SDK остаётся как эталон для
сравнения. Скорость окончательно проверяется только на консоли.

## Что берём из masseffect-nx

Общие части `app/src/native/` (~56 тыс. строк): разбор PM4, EDRAM mode 4, кэш текстур, кэш пайплайнов, отложенная
запись. Специфичное для Mass Effect (хуки Direct3D UE3, опознание шейдеров, проходы движка) пишется заново.
Инструменты шейдеров (`shaders/`: XenosRecomp с правками, упаковщик) в локальной копии репозитория отсутствуют —
их нужно взять из github.com/NebadasSwifty/masseffect-nx.

## Риски

- Даже при цене draw как у masseffect-nx 3900 draw дают ~15–20 fps; без этапов 4–5 цели не достичь.
- Цена потоков самой игры на A57 не измерена — если она > 33 мс на кадр, рендер не поможет (нужна оптимизация
  сгенерированного кода).
- Без консоли скорость оценивается только косвенно.

## Ход работ

### Этап 1 — библиотека шейдеров (2026-11-08, начат)

- `port/tools/sdshaders.py` — извлечение контейнеров из `.big`: **2147** различных (1076 VS, 1071 PS), все в
  `Global` и `SeekFreeBoot`.
- XenosRecomp (из masseffect-nx) → HLSL: 2139 из 2147 (8 падают). DXC 1.9.2609 + spirv-val → SPIR-V: **2137**
  (2 VS с выборкой текстуры без явного LOD — исправимо). Скрипт: `port/tools/shaderlib/build_shaderlib.sh`.
- Покрытие по рантайму (дамп микрокода `SDNX_DUMP_UCODE=<папка>` на стенде): **PS 173 из 174** совпали байт в байт
  (хэш XXH3 микрокода как в SDK); **VS 182 из 184** совпали при маске на инструкциях `vfetch` — Direct3D вписывает
  в них формат/смещение/шаг при привязке (как в Mass Effect). Совпадения VS неоднозначны (одинаковый код в
  нескольких контейнерах) — нужен хук на привязку шейдера в Direct3D игры (этап 2). 2 VS без совпадения — 24–27
  слов, вероятно внутренние шейдеры Direct3D.
- **Опознание VS без хуков (2026-11-08):** для каждого рантайм-VS все подходящие контейнеры (маска на `vfetch`)
  совпадают в таблице литеральных констант, входах, интерполяторах и заголовке — годится любой кандидат.
  Но HLSL зависит от вписанного Direct3D раскладки компонент `vfetch` (пример: `.xyzw` → `.xyz` + `w = 1`,
  texcoord `.xy` → `.yx`), т.е. переводить VS из контейнера как есть нельзя. Решение на выбор:
  (а) библиотека вариантов (рантайм-микрокод в контейнер-кандидат → трансляция; ключ — XXH3 рантайм-микрокода)
  плюс режим сбора новых вариантов при игре, как в masseffect-nx;
  (б) правка транслятора: раскладка компонент `vfetch` применяется в рантайме через уже существующий
  `remapInput(..., g_InputRemap(i))` — одна трансляция на контейнер для всех вариантов. Предпочтительно (б).
- Вылет `0x8244EDE0` исправлен и проверен пользователем в игре.
- **Транслятор: динамическая выборка вершин (2026-11-08, сделано).** Решение (б). Транслятор перенесён в
  `nx/shaders` (XenosRecomp из masseffect-nx, MIT), правки под `SDNX_FETCH_SWIZZLE`:
  - `vfetch` пишет весь регистр через `fetchApply(r, value, g_FetchSwizzle(K))`; код раскладки (12 бит, 0–3
    компонента, 4 = 0, 5 = 1, 6/7 = не трогать) рендер берёт из рантайм-микрокода; коды лежат в общем блоке
    констант с байта 496 (по 2 на слово, до 32 выборок; блок расширен до `float4 v[35]`).
  - В конце HLSL — `// SDNX_FETCH_ORDER: адрес:регистр:маска` для каждого `K`. Direct3D может переставить
    выборки одного потока (мини-выборки по смещению — 23 шейдера из 182), поэтому рендер сопоставляет
    рантайм-выборки с `K` по регистру назначения, при повторе — по наибольшему пересечению масок.
    Проверено на всех 182 рантайм-VS: сопоставление однозначно.
  - Точное определение выборок — по потоку управления (`port/tools/shaderlib/vsmatch.py`); маска только по
    коду операции давала ложные совпадения с ALU.
  - VS с выборкой текстуры: `SampleLevel(…, 0)` в вершинной стадии.
  - Библиотека пересобрана: **2139 HLSL → 2139 SPIR-V, 0 ошибок** (8 контейнеров не переводятся).
- **Осталось по шейдерам:** 5 рантайм-VS делают косвенную выборку (индекс не `r0`, а регистр, загруженный
  предыдущей «ручной» выборкой — похоже на инстансинг); 2 из них транслятор отвергает, 3 переводит без учёта
  индекса. Нужна выборка из буфера памяти в шейдере (адрес из fetch-константы, формат из рантайм-слова) —
  этап 3, вместе с буфером памяти рендера. 1 рантайм-PS (`A4A965C189287B99`) нет среди контейнеров.

### Этап 2 — каркас (2026-11-08, начат)

- Бэкенд `sdnx` в SDK стенда (`D:\CODE\me-sdk`): `include/rex/graphics/sdnx/`, `src/graphics/sdnx/`
  (`NativeGraphicsSystem` + `NativeCommandProcessor`). Включение: `SDNX_NATIVE=1` или cvar `sdnx_native_renderer`.
  Код masseffect-nx не копируется (GPLv3) — основа на классах SDK (BSD): поток кольца, разбор PM4, регистры,
  прерывания, ожидания, запросы видимости остаются базовыми; заменены `LoadShader` (кэш по XXH3 микрокода),
  `IssueDraw` / `IssueCopy` (пока только счёт; резолв приходит как draw с `edram_mode == kCopy`), `IssueSwap`
  (заглушка: пульсирующая заливка через `Presenter`). Статистика `[sdnx_native]` раз в 5 с.
- Результат: игра работает без эмуляции отрисовки, 60 кадров/с, без вылетов; меню отвечает на START.
  Прогон с 40 нажатиями: заставки ~110 с (78–93 draw, 25 резолвов на кадр, нажатия не действуют), затем меню
  ~565 draw. На эмуляции та же игра уже через 15–20 с рисует ~3000+ draw (3D-сцена) — порядок загрузки
  отличается; без картинки причину не определить. Следующий шаг — настоящая отрисовка (сначала UI).
- `port/tools/fps_bench.ps1`: параметры `-LogLevel`, `-Presses`, `-StartKeyAt`.

### Этап 2b — дизайн отрисовки (2026-11-08)

1. **EDRAM-lite.** Рендер-таргет = Vulkan-образ на ключ (база EDRAM, шаг в тайлах, формат, MSAA); высота растёт
   по мере надобности. Перекрытия форматов на этом шаге не переносятся (правила Sleeping Dogs — этап 3).
   Резолв (`IssueCopy`): `draw_util::GetResolveInfo` → копия прямоугольника из образа-источника в «резолвенную
   текстуру» по физическому адресу назначения (образ размера назначения), затем очистка по `rb_copy_control`.
2. **Вывод.** `IssueSwap(frontbuffer_ptr)` → резолвенная текстура с этим адресом → blit в образ гостевого
   вывода (формат A2B10G10R10, layout SHADER_READ_ONLY).
3. **Draw.** Шейдеры из библиотеки (`port/shaders`: SPIR-V по XXH3 микрокода PS; VS — по маске `vfetch` к
   контейнеру + коды раскладки из рантайм-микрокода). Вершины/индексы копируются из памяти игры в момент draw
   с перестановкой байт; константы VS/PS и общий блок (`MASSEFFECT_UBO` = 1: UBO set 4) заполняются из
   регистров. Пайплайн по ключу состояния (blend, depth/stencil, cull, топология, форматы таргетов).
4. **Текстуры.** Загрузка из памяти игры с раскладкой тайлов Xenos и перестановкой байт, кэш по (адрес, формат,
   размер); дескрипторы — bindless-массивы (`g_Texture2DDescriptorHeap[]`).
- **Шаг 1 сделан (2026-11-08):** EDRAM-lite (образ на конфигурацию таргета), резолвы (`GetResolveInfo` → прямоугольник
  в пикселях из упакованной базы → `vkCmdBlitImage` в «резолвенную текстуру» по `RB_COPY_DEST_BASE`), очистки
  из резолва, вывод фронт-буфера (fetch-константа 0) compute-шейдером `src/graphics/sdnx/shaders/present.cs.hlsl`
  (образ гостевого вывода без `TRANSFER_DST` — только storage/attachment). В таблицу функций Vulkan SDK
  (`functions/device_1_0.inc`) добавлены blit, clear depth, draw indexed, привязка буферов и др.
  Прогон: фронт-буфер найден в 100% кадров, 25 резолвов и 23 очистки на кадр, 7 таргетов, 17 текстур.
  Глубинные резолвы пока пропускаются (нужна конвертация compute-шейдером).
- **Шаг 2 (дальше):** draw — пакет библиотеки шейдеров для рантайма (PS по XXH3 микрокода, VS по хэшу с маской
  `vfetch` + `SDNX_FETCH_ORDER`), интерфейс ресурсов XenosRecomp (push constants / UBO set 4, bindless set 0–3,
  spec constant 0), вершины/индексы из памяти игры, пайплайны.
